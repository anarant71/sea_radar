# Checkpoint 03 — Ключ, серверный reader и образец сообщения

**Архив:** `sea-radar-checkpoint-03-<sha>.zip`, где sha — коммит, в который входит эта запись
**Дата:** 2026-09-17  **Задачи:** B-08…B-10

## Запуск

```bash
npm install
npx playwright install chromium   # браузер для тестов; Playwright обновился и требует докачки
npm run dev                       # http://localhost:3000
curl -s http://localhost:3000/api/snapshot
npm test                          # браузерные тесты выбора, dev-сервер поднимается сам
```

Ключ источника — переменная `AISSTREAM_API_KEY`. Без неё демонстрационная часть открывается как раньше, а `/api/snapshot` отвечает кодом `no_api_key`.

## Что сделано

- `.env.example` со строкой `AISSTREAM_API_KEY=` без значения лежит в репозитории и отслеживается git; `.env`, `.env.local`, `.env.*.local` игнорируются (`git check-ignore`).
- В `.claude/settings.json` три правила `deny`: `Read(./.env)`, `Read(./.env.local)`, `Read(./.env.*.local)`. Файла раньше не было, создан с нуля.
- Ключ читается в одном месте — `src/server/apiKey.ts`, `process.env.AISSTREAM_API_KEY`; пустая строка и пробелы считаются отсутствием ключа. Других обращений к `process.env` в `src/` нет.
- `GET /api/snapshot` — Route Handler на Node runtime: открывает WebSocket к AISStream, сразу после открытия отправляет подписку на район из конфигурации с фильтром `PositionReport`, возвращает первое полученное сообщение без преобразования в форме `{ ok: true, raw, collectedAt }`.
- Ошибки — HTTP 502 `{ ok: false, attemptedAt, error: { code, message } }`; пять кодов и текстов заданы литералами в `src/server/snapshotError.ts` и нигде не повторяются. Сырой текст ошибки источника или исключения в `message` не подставляется.
- Соединение и часы — параметры `readFirstMessage` (`src/server/reader.ts`), а не импорты: сетевого кода и вызовов `Date` модуль не содержит.
- Результат чтения завершается один раз: единственная функция завершения снимает таймер и закрывает соединение, поздние сообщения, закрытие и срабатывание таймера его не меняют.
- Срок 15 с отсчитывается от входа в чтение, до открытия соединения; константа — `SNAPSHOT_WINDOW_SECONDS` в `src/config.ts`, там же адрес потока и границы подписки, собранные из существующего `AREA_BOUNDS`.
- Кадры, у которых `MessageType` не равен `PositionReport`, пропускаются, и чтение продолжается до конца срока.
- Библиотека `ws` не добавлена: в Node 22 `WebSocket` доступен глобально. Прямые зависимости проекта не изменились.
- `data/samples/position-report.sample.json` — сообщение в исходной структуре: порядок ключей и значения как пришли, добавлены только отступы. Записан программно из поля `raw` ответа, без ручного перенабора.
- `data/samples/PROVENANCE.md` — время получения UTC, район подписки, факт живого получения, восемь отличий структуры от документации AISStream.

## Что осталось за рамками

- Правила `deny` из `.claude/settings.json` в бою не проверены: фиктивный `.env.local` не создавался, отказа от харнесса не наблюдалось. Оба отказа на запросы ключа были решением агента, не конфигурации. Проверка из SPRINT-02 (стр. 84) не выполнена.
- Ветки `provider_error` и `connect_failed` на живом источнике не воспроизводились: наблюдались только `no_api_key`, `disconnected` и успех. В коде ветки есть, на экране не появлялись.
- Ветка `raw: null` (соединение живо, подписка отправлена, сообщений за 15 с нет) не наблюдалась: оба успешных запроса вернули сообщение раньше конца срока.
- Отмена запроса клиентом не проверялась: путь `AbortSignal` написан, ни одного прерванного запроса не выполнялось.
- Закрытие соединения и снятие таймера во всех исходах автоматически не проверены: отдельного наблюдения за сокетами и таймерами после ответа не велось.
- Пропуск кадра `SubscriptionConfirmation` не наблюдался: в обоих успешных запросах первым разобранным кадром был `PositionReport`.
- Преобразование сообщения в структуру судна не писалось — задача B-11.
- Накопление нескольких сообщений не писалось — задача B-12.
- Интерфейс, карта и карточка не изменялись: кнопки загрузки и подписей R2 нет — задача B-13.
- Тестов на серверный код нет: раннер прежний, в `tests/` только три теста выбора из B-07.

## Отклонения от задания

- SPRINT-02, стр. 23 «Подтверждения подписки источник не присылает» → reader пропускает все кадры, кроме `PositionReport`, и ждёт дальше → документация AISStream и AsyncAPI-схема утверждают обратное: подтверждение присылается и не содержит `MetaData`. Если отдавать первый любой кадр, в `raw` попал бы служебный кадр и образец для B-10 из него не вышел бы.
- SPRINT-02, стр. 24 «`.env.local` с настоящим значением» → действующий ключ лежит в `.env` → файл создан вне занятия; `.gitignore` его игнорирует, в репозиторий он не попадает. Расположение заданию не соответствует.
- Критерий B-09 «ключа сейчас нет, поэтому запрос должен вернуть 502 с кодом `no_api_key`» → ветка проверена отдельным запуском с явно пустой переменной → ключ в окружении был задан, Next.js загружал `.env` (строка `Environments: .env` при старте), и условие ветки не выполнялось.
- `.gitignore`: к шаблону `.env*` добавлено исключение `!.env.example` → без него git игнорировал и шаблон, и критерий «`.env.example` в git» не выполнялся.
- Влияет на невыданные задания: да. Для B-11 существенны отличия из провенанса: регистр координат различается между `MetaData` (строчные) и `Message.PositionReport` (заглавные); `time_utc` приходит Go-рендером с дробной частью переменной длины (в образце 9 знаков, в документации 6); `ShipName` добит пробелами до 20 символов; `MMSI_String` приходит числом. Для B-13 существенно, что кода для отвергнутого ключа в контракте нет.

## Открытые вопросы

- Отвергнутый источником ключ и обрыв связи дают один код `disconnected` и один текст «Соединение с источником разорвано». Пользователь с испорченным ключом прочитает сообщение о связи. Нужен ли шестой код — решение заказчика; списки кодов и текстов в SPRINT-02 заданы закрыто.
- Отмена запроса возвращает код `internal` («Внутренняя ошибка сервера»). Ответ при отмене никто не читает, но по смыслу код неточен; отдельного кода для отмены в задании нет.
- Код закрытия WebSocket в `onClose` не читается, поэтому отличить отказ по ключу от сетевого обрыва сейчас нечем. Какой код закрытия присылает AISStream в каждом случае, не выяснялось.
- Расхождение по `SubscriptionConfirmation` (стр. 23) требует отметки в задании или устного подтверждения.
- Вопрос из checkpoint 01 и 02 остаётся: у карты задан `maxBounds` по границам района; задание такого ограничения не требовало и не запрещало.
